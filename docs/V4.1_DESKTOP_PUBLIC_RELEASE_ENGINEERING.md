## 1. Executive Summary & Zero-Fabrication Mandate

KyvonOPS V4.1 is a local-first infrastructure control plane built on **Rust 2021**, **Tauri 2**, **React 19 / TypeScript**, **SQLite (WAL mode)**, **direct SSH (`russh`)**, and a **policy-controlled Model Context Protocol (MCP) gateway**. 

Unlike web-centric SaaS management platforms, KyvonOPS executes privileged infrastructure operations directly from the operator's desktop workstation. This architectural decision places strict requirements on desktop release engineering:

1. **Zero Fabrication Invariant (`PROMPTS.md` §108)**: No installer download links, checksums, test passes, or production deployments may be claimed without genuine cryptographic, physical, or pipeline evidence.
2. **Local-First Credential Isolation**: SSH private keys, certificates, and API tokens must never touch the local SQLite database, application log streams, frontend state memory, or MCP agent contexts. They reside strictly within OS-native keychains.
3. **Fail-Closed Verification**: Binary downloads, auto-update packages, and agent bootstraps require mandatory SHA-256 and Ed25519 cryptographic signature verification prior to staging or execution.

### 2.2 macOS Packaging (`.dmg` and `.app`)

#### 2.2.1 Architecture & Universal Binary
macOS bundles are compiled for both Apple Silicon (`arm64`) and legacy Intel (`x86_64`). In CI/CD release workflows, bundles are combined into a Universal 2 binary using `lipo` to ensure zero friction across Mac hardware:

```sh
# Universal binary generation flow
lipo -create \
  target/x86_64-apple-darwin/release/bundle/macos/KyvonOPS.app/Contents/MacOS/kyvon-ops \
  target/aarch64-apple-darwin/release/bundle/macos/KyvonOPS.app/Contents/MacOS/kyvon-ops \
  -output KyvonOPS-Universal
```

#### 2.2.2 Hardened Runtime & Entitlements
To run cleanly on macOS without Gatekeeper blocking, the app bundle must be compiled with Hardened Runtime enabled and signed with a valid Apple Developer ID Application certificate.

Entitlements required (`apps/desktop/src-tauri/Entitlements.plist`):
```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <!-- Outgoing TCP network access for SSH (russh) to infrastructure nodes -->
    <key>com.apple.security.network.client</key>
    <true/>
    <!-- Local server bind for internal IPC & localhost preview -->
    <key>com.apple.security.network.server</key>
    <false/>
    <!-- Native Keychain integration -->
    <key>keychain-access-groups</key>
    <array>
        <string>$(AppIdentifierPrefix)com.kyvon.ops</string>
    </array>
</dict>
</plist>
```

#### 2.2.3 Codesigning & Notarization Pipeline
1. **Codesign with Hardened Runtime**:
   ```sh
   codesign --deep --force --verify --verbose \
     --options runtime \
     --entitlements apps/desktop/src-tauri/Entitlements.plist \
     --sign "Developer ID Application: Kyvon Inc (TEAMID1234)" \
     "target/release/bundle/macos/KyvonOPS.app"
   ```
2. **DMG Generation**:
   Packaged via `hdiutil` or Tauri DMG packager, styled with 540x380 background, custom icon positioning, and `/Applications` symlink.
3. **Apple Notary Service Submission**:
   ```sh
   xcrun notarytool submit "target/release/bundle/dmg/KyvonOPS_4.1.0_universal.dmg" \
     --apple-id "$APPLE_ID" \
     --team-id "$APPLE_TEAM_ID" \
     --password "$APPLE_APP_SPECIFIC_PASSWORD" \
     --wait
   ```
4. **Staple Ticket**:
   ```sh
   xcrun stapler staple "target/release/bundle/dmg/KyvonOPS_4.1.0_universal.dmg"
   ```

### 2.3 Windows Packaging (`.exe` NSIS Installer)

#### 2.3.1 NSIS Installer Specification
The Windows release utilizes NSIS (Nullsoft Scriptable Install System) bundled by Tauri.

Configuration in `tauri.conf.json`:
```json
"windows": {
  "nsis": {
    "languages": ["en-US"],
    "displayLanguageSelector": false,
    "installMode": "currentUser",
    "installerIcon": "icons/icon.ico",
    "headerImage": "icons/nsis-header.bmp",
    "sidebarImage": "icons/nsis-sidebar.bmp"
  }
}
```

* **Default Installation Path**: `%LOCALAPPDATA%\Programs\KyvonOPS` (per-user install, avoids UAC elevation prompts for ordinary updates).
* **Silent Enterprise Install Argument**: `KyvonOPS_4.1.0_x64-setup.exe /S /D=C:\Program Files\KyvonOPS`
* **WebView2 Runtime**: Relies on Evergreen WebView2 pre-installed on Windows 10 (version 1809+) and Windows 11. If absent, the NSIS bootstrapper automatically downloads and runs the Evergreen WebView2 installer.

#### 2.3.2 Authenticode Signing
Windows executables and NSIS installers must be digitally signed with an Authenticode certificate (Standard or EV):
```powershell
signtool.exe sign /v /fd SHA256 /tr http://timestamp.digicert.com /td SHA256 /sha1 <CERT_THUMBPRINT> "target\release\bundle\nsis\KyvonOPS_4.1.0_x64-setup.exe"
```

## 3. Native Installer, Signing & Checksum Flow

To prevent supply-chain tampering and man-in-the-middle attacks, every release asset is bound to a cryptographically signed digest manifest.

### 3.1 Checksum & Signature Pipeline

```text
┌────────────────────────┐
│ Built Release Binaries │
│  • .dmg (macOS)        │
│  • .exe (Windows)      │
│  • .AppImage (Linux)   │
│  • .deb (Debian)       │
└───────────┬────────────┘
            │
            ▼
┌──────────────────────────────────────────────────────────┐
│ SHA256 Generation                                        │
│ sha256sum KyvonOPS_* > SHA256SUMS                        │
└───────────┬──────────────────────────────────────────────┘
            │
            ▼
┌──────────────────────────────────────────────────────────┐
│ Minisign / GPG Signature Creation                        │
│ minisign -Sm SHA256SUMS -s kyvon_release.key             │
│ (Produces SHA256SUMS.minisig)                            │
└──────────────────────────────────────────────────────────┘
```

### 3.2 Linux Installer Fail-Closed Verification (`scripts/install.sh --desktop`)

The repository's master installation script implements strict validation before any binary touches user disk:

```sh
# Verification logic implemented in scripts/install.sh
fetch_and_verify_desktop() {
    local version="$1"
    local os_arch="$(uname -m)"
    local base_url="https://github.com/Filip2k03/kyvon_ops/releases/download/v${version}"
    local asset_name="KyvonOPS_${version}_${os_arch}.AppImage"

    echo "==> Fetching SHA256SUMS manifest..."
    curl -fsSL "${base_url}/SHA256SUMS" -o "/tmp/SHA256SUMS" || {
        echo "ERROR: Missing SHA256SUMS manifest for release v${version}. Aborting." >&2
        return 1
    }

    echo "==> Fetching binary asset: ${asset_name}..."
    curl -fsSL "${base_url}/${asset_name}" -o "/tmp/${asset_name}" || {
        echo "ERROR: Asset ${asset_name} does not exist in release v${version}. Aborting." >&2
        return 1
    }

    echo "==> Verifying SHA-256 digest integrity..."
    (cd /tmp && grep "${asset_name}" SHA256SUMS | sha256sum -c -) || {
        echo "SECURITY ALERT: Checksum verification failed for ${asset_name}!" >&2
        rm -f "/tmp/${asset_name}" "/tmp/SHA256SUMS"
        return 2
    }

    echo "==> Installing verified binary to ~/.local/bin/kyvon-ops..."
    mkdir -p "$HOME/.local/bin"
    install -m 0755 "/tmp/${asset_name}" "$HOME/.local/bin/kyvon-ops"
    rm -f "/tmp/${asset_name}" "/tmp/SHA256SUMS"
    echo "==> KyvonOPS successfully installed."
}
```

### 4.2 Ed25519 Cryptographic Signature Verification
* **Public Key**: Baked directly into `apps/desktop/src-tauri/tauri.conf.json` under `bundle.updater.pubkey`.
* **Private Key**: Held securely in release CI secret `TAURI_SIGNING_PRIVATE_KEY`.
* Every downloaded update archive is verified against the embedded public key *before* unpacking into the staging directory.

### 4.3 Atomic Staging & Rollback Strategy

To prevent corrupted updates from bricking the operator's control plane:

1. **Download & Verify**: Package is downloaded to an isolated temporary directory:
   `~/.local/share/com.kyvon.ops/updates/pending_v4.1.0/`
2. **Signature Verification**: Tauri updater verifies the Ed25519 signature against `bundle.updater.pubkey`.
3. **Pre-Flight Database Check**: The local SQLite database schema version is checked against required migration targets.
4. **Backup Current Executable**: The active binary is hardlinked or renamed to `kyvon-ops.backup-v4.0.9`.
5. **Atomic Swap**: The verified new binary replaces the current binary using atomic POSIX `rename()` or Windows pending-file-rename operations.
6. **Automatic Rollback Drill**: If the newly launched version fails its internal health check (`PRAGMA integrity_check` or backend panic within 15 seconds), the launcher automatically re-links `kyvon-ops.backup` and alerts the operator.

## 5. Strict Local-First Security & Credential Boundary

KyvonOPS adheres strictly to the security architecture specified in `docs/V4.1_SECURITY.md`.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        SECURITY PRIVILEGE BOUNDARY                     │
│                                                                        │
│   DESKTOP UI / CLI / MCP                                               │
│             │                                                          │
│             ▼                                                          │
│   Typed Intent (Actor, Target, Action, Args)                           │
│             │                                                          │
│             ▼                                                          │
│   Risk Classification Engine (kyvon-security)                          │
│   ├─ GREEN   (Read / Diagnostic)  ──> Execute & Audit                 │
│   ├─ YELLOW  (Low-impact mutate)  ──> Operator Notice & Audit          │
│   ├─ ORANGE  (High-impact mutate) ──> Modal Confirmation Required      │
│   └─ RED     (Destructive mutate) ──> Typed Control Gate Blocked       │
│             │                                                          │
│             ▼ (Orange / Yellow Confirmed)                              │
│   OS Keychain Credential Retrieval (com.kyvon.ops)                     │
│   • Password / SSH key retrieved into zeroize memory buffer            │
│   • NEVER persisted in SQLite WAL                                      │
│             │                                                          │
│             ▼                                                          │
│   russh Native SSH Transport                                           │
│   • Strict Host-Key verification (known_hosts)                         │
│   • Strict timeouts & stdout size caps                                 │
│             │                                                          │
│             ▼                                                          │
│   Post-Flight State Verification                                       │
│   • Check systemctl is-active / process status                         │
│             │                                                          │
│             ▼                                                          │
│   SQLite Audit Record (Redacted)                                       │
│   • Command, actor, timestamp, sanitized status recorded               │
│   • All credentials, tokens, private keys stripped via regex filter   │
└────────────────────────────────────────────────────────────────────────┘
```

### 5.1 Credential Storage Invariants
* **Never in SQLite**: The SQLite database (`~/.local/share/com.kyvon.ops/kyvon.db`) stores only node metadata (IP, port, username, host key fingerprints, tags, notes). It contains zero SSH passwords, private key PEM data, or API keys.
* **Native Keychain Binding**:
  * macOS: Apple Keychain via `Security.framework` (`SecItemAdd`, `SecItemCopyMatching`).
  * Windows: Windows Credential Manager via `wincred.h` (`CredWriteW`, `CredReadW`).
  * Linux: FreeDesktop Secret Service API over D-Bus (`org.freedesktop.secrets`).
* **In-Memory Zeroization**: Memory containing decrypted private keys is wrapped in `zeroize::ZeroizeOnDrop` buffers to prevent residual traces in process core dumps.

### 5.2 MCP (Model Context Protocol) Isolation
* The MCP server (`apps/mcp/`) operates under the same control gate as the desktop UI.
* AI contributors (**Codex Astra**, **Claude Opus**, and **Agy Gemini 3.8**) have access only to typed diagnostic tools (`probe_host`, `get_telemetry`, `list_services`).
* **Unrestricted Shell Execution is Prohibited**: There is no `exec_shell` or `run_command` tool exposed over MCP. Mutating tools (`assess_service_action`, `start_service`, `stop_service`) enforce mandatory schema validation and operator approval gates.

## 6. Build & CI/CD Pipeline Automation

The multi-platform release is automated via GitHub Actions in `.github/workflows/release.yml`.

### 6.1 Trigger & Prerequisites
* Trigger: Semantic version git tag push (`git push origin v4.1.0`).
* Matrix runners:
  * macOS: `macos-latest` (`universal-apple-darwin`)
  * Linux: `ubuntu-22.04` (`x86_64-unknown-linux-gnu`)
  * Windows: `windows-latest` (`x86_64-pc-windows-msvc`)

### 6.2 Pre-Flight Quality Gates
Before any bundle is packaged, the CI runner executes the strict test suite:
```sh
# 1. Rust workspace formatting and clippy
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings

# 2. Rust unit and integration test suite (200+ tests)
cargo test --workspace --all-features

# 3. Desktop frontend typecheck, build, and unit tests
cd apps/desktop
bun install --frozen-lockfile
bun run build
bun test
```

### 6.3 Local Manual Build Verification Commands

Operators building from source verify the build on their local workstation using:

```sh
# macOS Local Build
git clone https://github.com/Filip2k03/kyvon_ops.git
cd kyvon_ops
./scripts/install.sh --frontend
cd apps/desktop
bun run tauri build --bundles dmg,app

# Linux Local Build (Debian/Ubuntu)
```
